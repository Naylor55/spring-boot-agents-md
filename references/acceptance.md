# 验收清单

同一份清单，两种用法：Agent 在输出代码前用它自检，Reviewer 在 PR 上用它验收。

## 一、开发前（Agent 读完代码再动手）

- [ ] 已确认 `pom.xml` / `build.gradle` 中的 JDK 版本与 Spring Boot 版本，未使用超出版本的语法或 API。
- [ ] 已确认项目按领域组织还是按技术分层，本次代码落在了正确的包下。
- [ ] 已确认持久层选型：`mapper`（MyBatis / MyBatis-Plus）还是 `repository`（JPA），未混用。
- [ ] 已找到至少一个同类业务的 Controller / Service / Mapper 实现作为参照。
- [ ] 已确认统一返回体、统一异常、日志、参数校验、权限控制的现有写法。
- [ ] 已搜索项目内是否已有本次要新增的工具方法、常量或枚举。
- [ ] 需求中的业务规则都能在代码、文档或数据库注释中找到依据；找不到的已提出，而不是自行编造。

## 二、提交前自检（Agent 输出说明里逐条回答）

- [ ] 改动文件清单与任务范围一致；发现但未处理的问题已单列，未夹带重构。
- [ ] 新增依赖数量为 0，或已说明必要性。
- [ ] 未新增空目录；未创建项目用不上的 `mq` / `oss` / `job` 等（按需）目录。
- [ ] Lombok：未在已有 `@Data` / `@Getter` 的类里手写 getter/setter；日志字段用项目统一的 Lombok 注解。
- [ ] 依赖注入使用构造器方式（如 `@RequiredArgsConstructor` + `final`），无新增字段注入。
- [ ] Controller 中没有 Mapper / Repository 调用、没有跨表组装和业务计算。
- [ ] Service 承担事务边界；事务注解标在合适的公开方法上，未依赖自调用生效。
- [ ] 未新增 Handler / Manager / Factory / Assembler 等转发层，或已说明其隔离目的。
- [ ] 异常使用项目统一业务异常 + 错误码，未用 `RuntimeException` 兜底，未吞异常。
- [ ] 日志使用项目统一日志注解，无 `System.out.println`，未打印密码 / Token / 密钥。
- [ ] 查询未用 `select *`，分页有上限，循环内未做单条查询。
- [ ] 未擅自修改表结构、索引、数据迁移脚本；如涉及，已在方案中单独列出待确认。
- [ ] 对外响应未暴露 Entity 或敏感字段；兼容性变更已说明影响面。
- [ ] 引用的现有工具类、常量、枚举确实存在且用法一致。
- [ ] 按项目测试策略执行了验证（写单测或至少完成模块构建），并在总结中写明实际执行的命令与结果；未执行则明确说明原因，不声称「测试通过」。

## 三、Reviewer 验收（PR 上逐条确认）

- [ ] 目录归属正确：新代码在对应业务领域下，而不是一股脑塞进 `controller` / `service` 顶层。
- [ ] 模型使用正确：入参用 `param`，出参用 `vo`，持久化用 `entity`，没有拿 Entity 当接口出入参。
- [ ] 命名符合 Java 约定，无拼音混杂、无 `temp` / `data1` / `flag2` 一类名字。
- [ ] 没有为了「以后可能用到」而预留的接口、抽象类、配置项。
- [ ] 空值处理明确：区分 `null` / 空集合 / 空字符串，未返回 `null` 集合。
- [ ] 注释解释的是为什么，不是复述代码；无与实现不一致的注释。
- [ ] diff 中没有格式噪音（大段重排、无关 import 变动）。
- [ ] 有跨端 / 跨系统调用时，超时、重试、降级有明确处理。

## 四、验证规范本身是否生效（接入后第一次必做）

不要问 Agent「你是否理解规范」。选一个真实小需求，例如「新增一个按状态分页查询订单的接口」，然后检查：

- [ ] 代码落在 `order` 领域，而不是新建一个 `query` 包。
- [ ] 入参用 `param` + Bean Validation，出参用 `vo` + 统一响应，未暴露 `entity`。
- [ ] 持久层走项目既定选型，未凭空多出一套。
- [ ] Lombok、构造器注入、日志、异常均符合项目现有写法。
- [ ] 没有新增工厂类、接口层或空目录。
- [ ] 改动文件数量在预期范围内。

哪一项没过，回到 `AGENTS.md` 对应章节，把它改得更具体——通常不是 Agent 不听话，而是那条规则写得没法判定。

## 五、规范覆盖不到时

- 项目事实与模板冲突：以项目现有约定为准（`AGENTS.md` 第 12 节），并把该约定补写进项目自己的规则文件。
- 规则互相矛盾：先确认哪条是项目级约定，删掉或改写另一条，不要两条并存。
- 规则无法判定对错（如「代码要优雅」）：改写成可检查的形式（结构、命名、边界、行数），或者删掉。
- 规则长期没人违反也没人参考：删掉。规范的价值在于被执行，不在于全面。
